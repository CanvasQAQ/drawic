# Drawic agent development workflow

This handbook is the operational guide for local implementation agents. It
describes the repository as it exists now and the rules for changing it safely.
Paths are repository-relative. Do not add machine-specific paths or credentials
to this document.

## 1. Product and current state

Drawic is a local-first desktop editor for schematic and free-form drawing. It
uses independent pages and a single-file device library. The current source
version is authoritative in `package.json`.

Implemented:

- multi-page documents with page create, rename, duplicate, delete, reorder, and
  switching;
- searchable device library with 109 primary device records and 11 alternate
  appearances;
- component placement, marquee selection, multi-selection, movement, deletion,
  rotation, horizontal/vertical mirroring, duplicate mode, and Ctrl-drag copying;
- pointer-centered zoom, panning, placement previews, exact port selection, and
  port-to-port wiring;
- shared endpoint resolution and movement plans for connected wires, including
  rigid internal paths, local boundary stretching, segment handles, drag
  previews, network highlighting, explicit junctions, named nets, attached
  labels, and arc hops for electrically separate crossings;
- obstacle-aware orthogonal routing for newly created wires, including a
  minimum pin escape that is reapplied on every automatic routing pass;
- independently movable/hideable device labels plus directly editable text,
  rectangle, and ellipse objects with resize handles;
- component Reference Name labels with persisted default/automatic placement,
  rich typographic suffixes, GUI/Agent collision policies, and document-level
  sans/serif scaling, plus a Lexical-based direct segment rich-text editor;
- a custom cross-platform window title bar with native macOS traffic lights,
  local light/dark theme switching, and responsive canvas viewBox sizing;
- persisted per-Net wire colors shared by every wire and preserved in SVG
  export;
- a built-in device pin direction audit with visible escape arrows and JSON
  correction export;
- a bottom session console for placement, file, import/export, and error logs;
- pointer-centered wheel zoom and `F` fit-to-content;
- project save/open, recovery, dirty-state close protection, SPICE import/export,
  ERC, and SVG/PNG/PDF export;
- draw.io `mxlibrary` conversion helpers for device libraries.

Not yet implemented in the UI:

- importing/exporting full draw.io multi-page documents;
- multi-object shape group editing and advanced connector routing parity with
  format-specific drawing tools;
- stable per-segment wire identities, direction-mode editing, and an explicit
  disconnection-move gesture;
- user-editable device libraries;
- Spectre/SCS, simulation, local MCP, and cloud services.

Do not describe a design goal as shipped behavior. Update this section when
capabilities materially change.

## 2. Architecture boundaries

### Core

`src/core/` is pure TypeScript:

- no Electron, Node.js, filesystem, network, or browser DOM dependency;
- document schema and validation;
- page and editor operations;
- undo/redo history;
- connectivity and ERC;
- SPICE conversion;
- SVG/PDF export generation.

Core code must remain deterministic and testable in isolation.

### Renderer

`src/renderer/` contains React and SVG UI code. It has no Node.js access. It
communicates with the desktop layer only through the typed bridge declared in
`src/shared/bridge.ts`.

Do not add `fetch`, WebSocket, external stylesheets, remote fonts, or remote
images. Device artwork must come from the bundled library.

### Preload

`src/preload/index.ts` exposes a fixed API through `contextBridge`. Add one
purpose-specific method per operation. Never expose raw `ipcRenderer`,
filesystem paths, shell commands, or a generic request function.

### Main

`src/main/` owns:

- window lifecycle and close protection;
- native dialogs;
- project read/write and atomic saves;
- recent-project storage;
- recovery checkpoints;
- raster/PDF conversion;
- session-level network blocking;
- packaging smoke hooks.

Validate IPC sender and every request shape in the main process.

### Generated device library

`src/renderer/assets/device-symbols/` is the approved SVG build input plus its
integrity ledger.

`src/renderer/assets/device-libraries/drawic-built-in.drawiclib.json` is the
single generated runtime library. It contains sanitized artwork, pin metadata,
label anchors, search terms, and SPICE metadata. It is generated by:

```bash
npm run build:devices
```

Never manually edit the generated library. Change
`scripts/build-device-library.mjs`, regenerate, and verify the resulting file and
tests.

The generated library is imported once by the renderer and indexed at startup.
Device artwork is rendered per placed instance. If per-record lazy loading is
added, document precisely when parsing and artwork loading occur.

Relevant library API:

- `parseDeviceLibrary` validates the canonical JSON library file.
- `loadDeviceLibrary` indexes records for rendering.
- `symbolById`, `suggestedReference`, and `defaultDeviceValue` support editor
  behavior.
- `deviceLibraryToMxLibrary` exports draw.io `mxlibrary` XML.
- `deviceToMxLibraryEntry` converts one record for draw.io tooling.
- `parseMxLibraryTitles` is a lightweight import inspection helper.

Built-in pin directions can be reviewed in the **Pin audit** screen. Its
correction export is described in
[`DEVICE_PIN_AUDIT.md`](DEVICE_PIN_AUDIT.md). Apply reported changes to the
source manifest and regenerate the library.

Extend this API rather than parsing generated JSON independently in renderer
components.

## 3. Document model

The current schema version and discriminator are defined in
`src/core/model.ts`.

Top-level shape:

```text
DrawicDocument
  schemaVersion
  kind
  id
  title
  createdAt
  modifiedAt
  pages[]
```

Each page owns:

```text
DrawingPage
  id
  name
  nodes[]
  nets[]
  annotations[]
  shapes[]
```

Each component owns:

```text
ComponentNode
  id
  symbolId
  reference
  value
  transform
  mirroredVertically?
  labelLayout?
```

`labelLayout` stores rendered label position, alignment, visibility,
default/manual placement, and visual typography. It does not replace the
electrical `reference`.

Each net owns:

```text
Net
  id
  name?
  color?
  wires[]
  junctions[]
```

Each wire is one polyline edge between two electrical endpoints:

```text
Wire
  id
  points[]
  start: pin | junction | open
  end:   pin | junction | open
```

Important invariants:

- at least one page always exists;
- all stable IDs are unique within a document;
- schema version 3 is the current format; version 2 is rejected;
- page switching is view state and does not modify the document;
- every wire belongs to exactly one net;
- a Net color is optional `#rrggbb` visual metadata and applies to every wire in
  that Net;
- a component Name is a bound visual label derived from its electrical
  Reference; visual styling never changes connectivity;
- a wire endpoint references a device pin, a junction in the same net, or an
  explicit open end;
- only genuine branch vertices are stored as junctions; degree-two joins are
  normalized into one wire;
- a crossing does not connect without an explicit junction;
- wire-to-wire endpoint overlap connects only through an explicit junction or
  shared net identity;
- a device pin touching a wire is an electrical contact;
- net names and Net Labels merge nets by matching text;
- every connected network exposes one canonical name to all member wires;
- cross-net crossings render arcs but never create stored topology;
- future schema versions are rejected;
- retired preview formats are rejected without migration.

Changing these invariants requires an ADR and updates to parser, editor,
connectivity, ERC, exports, renderer state, and tests.

Wire endpoint resolution, movement classification, local stretching, and
preview/commit behavior are defined in
[`WIRE_INTERACTION_MODEL.md`](WIRE_INTERACTION_MODEL.md), ADR 007, and ADR 008.
ADR 008 defines explicit junction, crossing-hop, and net-name semantics.

## 4. Device library rules

Each device record is self-contained. Keep all devices in library files; do not
split one device into several runtime files.

Required record data:

- stable device ID, title, category, and search terms;
- view box/frame;
- sanitized SVG artwork;
- pin ID, name, role, direction, and canonical local coordinates;
- unpadded visible-ink bounds including visible pins, plus an optional explicit
  Reference-label policy;
- reference/value label anchors;
- SPICE prefix, default value, and support state;
- source hash and provenance metadata.

SVG import requirements:

- allowlist supported SVG elements;
- remove scripts, event handlers, `foreignObject`, and external references;
- normalize fixed black strokes/fills to theme-aware values;
- preserve path/fill detail;
- do not execute conversion scripts from an untrusted asset package.

The draw.io `mxlibrary` adapter is an interoperability boundary. It may not
preserve all Drawic electrical metadata after arbitrary draw.io editing. Report
lossy conversion explicitly rather than claiming perfect round-trip.

When adding a device definition:

1. add or update the approved build input;
2. update the build script/record mapping if needed;
3. regenerate the single library;
4. verify its checksum stability by running the generator twice;
5. add a device-library test;
6. check library preview contrast and pin hit targets;
7. verify SVG/PNG/PDF and SPICE behavior where applicable.

Terminal-variant artwork declares `3terminal` or `4terminal` in its root
`data-variant` attribute. The source manifest's pin list is the electrical
definition; a 3-terminal appearance hides its bulk pin, while the corresponding
`base` appearance exposes D/G/S/B. The current library therefore ships both the
six default three-terminal MOS symbols and six four-terminal `--base`
alternates. Alternate appearances are separate stable symbol IDs and may be
selected from the device library when eligible.

## 5. Parallel agent ownership

Use one writer per file or tightly coupled module. Suggested ownership:

| Workstream | Owned paths |
| --- | --- |
| Core model | `src/core/model.ts`, `src/core/project.ts`, `src/core/editor.ts`, core tests |
| Connectivity/export | `src/core/connectivity.ts`, `src/core/erc.ts`, `src/core/spice.ts`, `src/core/export/` |
| Renderer | `src/renderer/**`, renderer tests |
| Device library | `src/core/library.ts`, `scripts/build-device-library.mjs`, generated library, library tests |
| Desktop bridge | `src/main/**`, `src/preload/**`, `src/shared/bridge.ts`, desktop tests |
| Release/docs | `package.json`, workflow, release notes, provenance and clean-room docs |

Before multi-agent work:

1. read `AGENTS.md` and this document;
2. run `git status`;
3. assign non-overlapping paths;
4. agree on shared interfaces before editing;
5. do not revert or reformat unrelated files;
6. merge through the main branch only after full validation.

If two agents must edit the same interface file, one owns it and the other sends
the required change. Do not race on the same file.

## 6. Standard development loop

1. State one verifiable goal.
2. Inspect the relevant code, tests, and ADRs.
3. Add or update tests with the behavior.
4. Implement the smallest coherent change.
5. Run the focused test.
6. Run strict typecheck.
7. Run the full test suite.
8. Run offline and clean-room audits.
9. Run the production build.
10. For desktop changes, run a packaged smoke test.
11. Review `git diff`.
12. Commit one logical goal with a focused message.

Suggested commit prefixes: `feat:`, `fix:`, `test:`, `docs:`, `build:`,
`refactor:`.

Do not commit `node_modules`, `dist`, `release`, test reports, recovery data,
local editor settings, or environment files.

## 7. Validation matrix

Fast feedback:

```bash
npm run typecheck
npm test
```

Full source gate:

```bash
npm run verify:offline
npm run verify:clean-room
npm run verify:docs
npm run build
```

Desktop directory-package smoke on headless Linux:

```bash
npm run dist:dir
xvfb-run -a npm run smoke:packaged
```

On Linux, when launching the Electron GUI or packaged smoke test as root,
restore the Chromium sandbox helper after `npm ci`, `npm install`, or deleting
and rebuilding `node_modules`:

```bash
chown root:root node_modules/electron/dist/chrome-sandbox
chmod 4755 node_modules/electron/dist/chrome-sandbox
```

Run this once after dependency installation or a `node_modules` rebuild. It is
not needed after `npm run build`, which uses the default permissions for
`dist/`.

Tagged distribution packages are produced on native Windows, macOS, and Linux
runners: Windows x64 ZIP, macOS x64/arm64 DMG/ZIP, and Linux x64 AppImage/DEB.
Each platform package smoke test runs in CI before publishing.

Release assembly:

```bash
npm run checksums
npm run verify:release
```

`verify:release` expects a fully assembled `release/` directory containing
Windows x64, macOS x64/arm64, and Linux x64 packages plus `SHA256SUMS.txt` and
`UNSIGNED-RELEASE.txt`.

  `tests/labels.test.ts`, `tests/componentLabel.test.tsx`

depend on the current clock, filesystem outside a temporary directory, network,
or developer-specific paths.

## 9. Security and privacy checklist

- renderer: sandbox, context isolation, no Node integration;
- preload: narrow typed methods only;
- main: validate sender and payload;
- no runtime network clients;
- no external export dependencies;
- no unvalidated filesystem paths from renderer input;
- SVG inputs sanitized;
- no secrets, tokens, certificates, usernames, host names, or absolute local
  paths in source, tests, logs, docs, commits, or release notes;
- CI uses platform-provided ephemeral credentials and never prints them.

Run the provided audits before committing security-sensitive changes.

## 10. Release procedure

1. Complete all code and documentation changes.
2. Update the version in `package.json` and `package-lock.json`.
3. Add release notes matching the exact tag: use
   `docs/release-notes-vX.Y.Z-preview.md` for a preview and
   `docs/release-notes-vX.Y.Z.md` for a formal release.
4. Update README capability and limitation statements.
5. Run all source, audit, build, and packaging gates.
6. Commit the release preparation.
7. Create and push an annotated tag: `vX.Y.Z-preview` for previews and
   `vX.Y.Z` for formal releases.
8. Wait for the tag-driven GitHub Actions workflow to succeed.
9. Confirm Windows, macOS, and Linux packages, checksum file, and unsigned notice
   are uploaded.
10. Download at least one final asset and verify its SHA-256 against the
    published checksum file.

Never publish a release when any build, test, packaged smoke test, or audit has
failed. Do not describe unsigned artifacts as signed.

Unsigned Windows and macOS artifacts still trigger SmartScreen and Gatekeeper
warnings until trusted signing identities and notarization are configured.

After a successful publish, CI retains only the newest Preview release and the
newest formal release. Older Release entries and their tags are removed
automatically. Draft releases are never pruned.

## 11. Clean-room and provenance

Read `CLEAN_ROOM.md`, `PROVENANCE.md`, and `THIRD_PARTY_NOTICES.md` before adding
external material.

- Use only approved asset inputs.
- Keep per-file hashes in the asset ledger.
- Record source, revision, distribution basis, and transformations.
- Do not copy source or screenshots from comparable editors.
- Public draw.io format/behavior documentation may inform interoperability, but
  imported code, templates, or artwork require separate license review.
- Update provenance and notices in the same change that adds external material.

## 12. Troubleshooting

Renderer is blank:

1. run `npm run typecheck`;
2. run `npm run build`;
3. check the renderer CSP;
4. check that the built preload and renderer paths match the compiled main
   process layout;
5. run the Electron smoke mode and inspect the report.

SVG appears black in the library:

1. inspect the record's sanitized SVG;
2. verify fixed fill/stroke was normalized;
3. verify `currentColor` and the preview color are applied to child elements;
4. regenerate the single device library.

Generated device library differs after regeneration:

1. do not hand-edit it;
2. find nondeterministic ordering, timestamps, paths, or float formatting in the
   generator;
3. run generation twice and compare SHA-256;
4. run device-library tests.

Wire does not bind:

1. inspect canonical pin coordinates in the device record;
2. verify `deviceId + pinId` exists;
3. verify transformed node pin position;
4. add a connectivity regression test.

Packaging fails locally:

1. use the native target platform;
2. for Linux smoke, provide a virtual display;
3. do not weaken sandbox/security settings to bypass a packaging problem;
4. inspect the failing target and CI log before changing configuration.
